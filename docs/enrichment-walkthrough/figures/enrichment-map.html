SAP customer master · name enrichment

How one SAP record gets enriched

Cheap and certain first, expensive and uncertain last. Models and web pages may propose a value; only registries and deterministic guards may authorise one. Every judgement is made once, at the end, from what the record actually holds.

Two boxes up close

The website guard and the address

Website + guard: six ways to tie a domain

A candidate website comes from ROR, a web search or a model's guess. It is accepted only if something ties it to this organisation. The conditions are checked in this order, and the first that holds wins.

  1. A registry supplied it. ROR's own website link, after ROR's guards passed.
  2. An independent source names the same site. ROR's links or Wikidata's official website equal the candidate. The only web-found domain that reaches verified.
  3. The name matches the domain. Name 1 against the domain label scores ≥ 82: lockheedmartin.com passes at 82.4, aumbiotech.com fails at 81.8.
  4. The record's own email says so. A company address such as orders@meridianlabs.com. Gmail, Outlook and other personal mail never count.
  5. A search result on that site carries the name. Every significant Name 1 word appears in the page title or H1.
  6. The site names itself. The page read finds this organisation's name, not placed in another state or country. provisional at most: a site vouching for itself is one source.

None holds → the domain still ships, at web:x:low with domain-unverified (informational, no review). One exception: if the page read found a different organisation, the domain is removed.

The address: inside the API, then after it

Addresses are handled in three places. Only the first two are part of this service, and neither calls an outside address service.

1 · Clean, before enrichment

  • Out of the name slots. A street, suite or PO box typed into Name 1–3 moves to the street fields.
  • Out of the street slots. An organisation or department typed into a street line moves to the name block.

2 · Address cleanup, in the funnel

  • Clean and extract (rules). Trim, then pull PO box, suite, building, floor, room, mail stop and c/o into their own fields; split a whole address jammed into one line.
  • Cross-check (rules). Duplicates, conflicts and names inside street lines are reported; nothing moves.
  • Model, only for leftovers. A Street 2–5 value that doesn't read as an address is classified. High confidence acts; low confidence only reports.
  • Normalise (rules). Street → St, North → N.

3 · Address validation, after write-back

Production step 6 validates addresses with the HERE API and writes back automatically above 80% confidence. It runs after this API, and its pipeline is not in this repository, so its exact rules can't be checked here.

Why batch consensus isn't on the map. It only compares rows that arrive in the same API call. Production sends 30 rows per call, ordered by customer code, so across roughly 100k records two rows for the same organisation rarely share a call. It does act on whole-workbook runs (the file upload and the evaluation script). Making records agree across the full dataset is the deduplication phase's job, which receives the whole group code in one call.

Reading any output value

How much to trust it

Every written field carries a provenance string, source:confidence[+witness]. One function decides the confidence, so it means the same thing in every row.

verified

A registry wrote it, or a second, independent source agrees.

ror:verifiedgleif:verified+wikidatainput:verified+web

No review. A model can never reach this rung.

provisional

One source, and nothing contradicts it.

web:acme.com:provisionalinput:provisional+llm

No review for names.

low

Nothing confirmed it, sources disagreed, or the name is too short to identify.

input:lowweb:site.com:low

Review when it is Name 1 or Name 2: low-confidence-unchanged.

Separately, any name a model wrote without a registry confirming it carries unverified-inference, whatever its rung. Two codes only inform and never queue a record: domain-unverified and registry-location-mismatch.

Why every decision goes the way it does

Six rules behind the map

The registry wins

A verified ROR or GLEIF match writes the official name. Only a registry can be verified on its own.

Models propose, never authorise

A model-written name is re-checked against a registry, or it ships flagged unverified-inference.

A wrong id is worse than none

Country, distinctive-token, acronym, short-name and ambiguity guards all ask one thing: is this the same organisation? If in doubt, no match.

Silence is not evidence

A page with no address, a 403, a missing headquarters: neutral, never a contradiction.

Never fabricate, never blank

If nothing improves a value, the input stays and a flag says so. A blank department stays blank.

Decide once, at the end

Tiers leave evidence. Flags, status and record type are computed in finalise from the final record.
